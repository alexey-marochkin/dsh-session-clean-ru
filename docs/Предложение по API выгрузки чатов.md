# Предложение для DSH: публичный API выгрузки и удаления чатов

> Перевод черновика от 13 октября 2026 года, подготовленного в [исходном проекте Ansellwan](https://github.com/Ansellwan/DeepSeekHarness-Session-Delete) после изучения `app.asar` настольной версии DSH `0.2.0-rc.2`.
> Это черновик обращения к разработчикам DSH, а не описание API текущей версии. Цель — дать сторонним плагинам способ полностью удалять чаты без обращения к внутренним полям.

## Кратко

В исследованной версии DSH нет публичного способа выгрузить чат из памяти хоста. Боковая панель показывает объединение записей из постоянного хранилища и `ctx.sessions.list()`, поэтому удаление файлов не убирает из списка чат, который остался в памяти. Нужен публичный API.

## На момент исследования: проверенные публичные интерфейсы

| Интерфейс | Доступные методы | Чего не хватает |
|---|---|---|
| `ctx.sessions` на хосте (`SessionStore`) | `registerMessageProjection`, `create`, `prepare`, `enter`, `announce`, `flush`, `get`, `list`, `fork` | Нет `remove`, `delete`, `unload`, `close` или `evict`. |
| `ctx.agents` на хосте (`AgentRegistry`) | `currentInitiator`, `requireInitiator`, `withInitiator`, `withoutInitiator`, `setFactory`, `create`, `resume`, `register`, `enter`, `announce`, `get`, `list`, `roots` | Нет снятия регистрации агента по идентификатору. |
| Клиентский `sessionController` | `list`, `search`, `create`, `rename`, `fork`, `prompt`, `attachment`, `cancel`, `page`, `follow`, `control` | `control` — поток кадров только для чтения; он не выполняет действий. |
| Клиентский `uiWorkspace` | Архивация, восстановление из архива, закрепление и открепление | Нет операции удаления чата. |
| `sessionPersistence` | Открытие, добавление записей, сброс на диск и закрытие | Нет `delete`: стороннему плагину приходится удалять каталоги напрямую через файловую систему. |

`cordis` не позволяет заменить зарегистрированный сервис (`service "…" has been registered`), поэтому таким способом встроить фильтр нельзя. У списка чатов также нет точки расширения `waterfall`.

## Почему это должен делать хост

- Пользователь ожидает, что удалённый чат нельзя будет восстановить и что он исчезнет из списка. Сторонний плагин может удалить файлы в обход слоя хранения, но хост управляет чатом в памяти, который по-прежнему попадает в список.
- Добавление идентификатора в `archivedSessionIds` только скрывает чат. Он остаётся виден при отображении архивных чатов, а восстановление из архива возвращает его в раздел «Без группы». Плагин не должен выдавать такое скрытие за удаление.
- Для разрушительной операции важен порядок завершения. В `dsh-agent-loop` обработчик жизненного цикла `dispose` следует цепочке: `machine.cancel({kind:'disposed'})` → `await machine.whenIdle()` → `await machine.scope.dispose()` → `await handle.close()` → `detachAgent()` → `detachSession()`. Стороннему плагину доступен лишь эквивалент последнего шага `detachSession`. Если выполнить только его, выгруженному чату всё ещё может соответствовать активная машина состояний в памяти.

## Предлагаемый интерфейс

Имена и формы результатов приведены как пример и не предписывают реализацию.

1. **Хост:** `ctx.sessions.unload(id)` (или `delete(id)`, `close(id)`).
   - Возвращать однозначный результат, например `{ unloaded: boolean, wasLive: boolean, detail }`.
   - Выполнять завершение в указанном порядке: отмена, ожидание простоя, освобождение области действия, закрытие дескриптора и снятие обеих регистраций. Одного `store.delete` недостаточно.
   - Если у чата есть незавершённая работа, возвращать явную причину отказа либо предоставить параметр `force`, чтобы вызывающая сторона не угадывала состояние.
   - Отправлять существующее событие `session/disposed`. Оно уже преобразуется в `api-session/removed`, а на клиенте — в изменение списка `{kind:'remove'}`.
2. **Слой хранения:** `ctx.sessionPersistence.delete(id)` (либо удаление как часть `unload`).
   - Удалять каталог чата, запись кэша проекций и её резервные копии, а также каталог `session-<hash>` с вынесенными на диск данными (`spill`).
   - Согласованно удалять запись из памяти домена хранения и с носителя. Кэш проекций записывает изменения отложенно: если удалить только файл, следующая контрольная точка восстановит его из памяти.
3. **Необязательно:** добавить `waterfall`-событие `session/list-filter`, чтобы плагины могли исключать идентификаторы из списка. Это временная мера, а не замена выгрузке на хосте.

## Совместимость

- Даже минимальный `sessions.unload(id)` без полного упорядоченного завершения и очистки постоянного хранилища позволил бы стороннему плагину сначала выгрузить чат, а затем удалить его файлы, не выдавая скрытие за удаление.
- Публичный метод нужно включить в генерируемый каталог `api-catalog` пакета `dsh-tool-cordis`. Тогда плагины смогут проверять наличие возможности и выбирать режим работы для разных версий DSH, не полагаясь на методы прототипа `liveEntryFor` и `detachEntered`, не входящие в контракт.

## Для сравнения: обходной путь исходного плагина

В `dsh-session-clean@1.1.2` (первая реальная выгрузка появилась в `1.1.0`) плагин проверял наличие `ctx.sessions.liveEntryFor(session).detach()` и вызывал его при наличии. Внутри происходили `store.delete`, `attachments.delete` и отправка `session/disposed`; строка действительно исчезала из боковой панели. Для очистки кэша плагин удалял запись из таблицы `sessions` по полному идентификатору чата, а не только файл кэша. Он также удалял соответствующий каталог `spill`. Если проверка возможностей не проходила, исходный плагин замораживал и скрывал чат и возвращал интерфейсу `unloaded: false`.

Публичный API устранил бы необходимость обращаться к внутренним методам и сообщать об этих обходных режимах.
